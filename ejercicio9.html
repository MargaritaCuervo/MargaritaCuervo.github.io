Ejercicio Guiado 9: Pruebas Read-heavy vs Write-heavy en Locust

1. Introducción

En este ejercicio nos enfocamos en analizar cómo varía el comportamiento del sistema PredictHealth ante dos patrones de tráfico opuestos: uno dominado por la lectura de datos (Read-heavy) y otro dominado por la inserción de datos (Write-heavy).

Esta distinción es vital porque las operaciones de escritura suelen ser más costosas para la base de datos (bloqueos, índices, integridad transaccional) que las de lectura. Comparar ambos escenarios nos permite identificar cuellos de botella específicos en la capa de persistencia.

2. Objetivos de la Prueba

  • Comparar Rendimiento (RPS): Medir la diferencia en la capacidad de procesamiento de peticiones (Throughput) entre un escenario mayoritariamente de lectura (90/10) frente a uno de escritura (20/80).
  • Evaluar Latencia de Escritura: Identificar cuánto aumenta el tiempo de respuesta cuando múltiples usuarios intentan escribir concurrentemente en la misma tabla (Doctores/Pacientes).
  • Identificar Cuellos de Botella en BD: Detectar si la base de datos PostgreSQL se convierte en el limitante debido a bloqueos (locks) o falta de optimización en los INSERTs.

3. Metodología

Arquitectura del Entorno de Prueba

Las pruebas se ejecutaron desde una máquina local que actuaba como nodo maestro de Locust, generando tráfico HTTP hacia los servicios desplegados. Los componentes del sistema (CMS y microservicios) estaban corriendo localmente a través de Docker Compose, lo que asegura un entorno aislado y consistente para la evaluación.

La arquitectura general de la prueba sigue el siguiente flujo:

[Máquina Local (Locust Master)] -> [Red Local (Docker Network)] -> [Contenedores de CMS y Microservicios] -> [Contenedores de PostgreSQL y Redis]

Las URLs base configuradas para cada servicio bajo prueba fueron las siguientes:

  • CMS: http://localhost:80
  • Servicio Auth-JWT: http://localhost:5000
  • Servicio de Instituciones: http://localhost:5001
  • Servicio de Doctores: http://localhost:5002
  • Servicio de Pacientes: http://localhost:5003

Herramientas Utilizadas

  • Locust: Versión 2.41.6
  • Infraestructura: Docker (v20.10+) y Docker Compose (v2.0+).
  • Backends: PostgreSQL (v15+), Redis (v6.0+).

4. Descripción de los Escenarios de Carga

Se definieron dos perfiles de usuario distintos en el archivo read_write_test.py, controlados mediante pesos (weights) en las tareas de Locust.

Escenario A: Read-Heavy (Lectura Intensiva)

  • Proporción: 90% Lectura / 10% Escritura.
  • Comportamiento: Simula un día típico de operación donde la mayoría de usuarios consulta información y pocos crean registros.
  • Tareas Clave: get_all_doctors (Peso 9), create_doctor (Peso 1).

Escenario B: Write-Heavy (Escritura Intensiva)

  • Proporción: 20% Lectura / 80% Escritura.
  • Comportamiento: Simula un evento de alta demanda de registro, como una campaña de vacunación o migración de datos.
  • Tareas Clave: create_patient (Peso 8), get_patient_details (Peso 2).

5. Código Generado

Archivo read_write_test.py

El script utiliza el decorador @task(peso) para manipular la probabilidad de ejecución de cada endpoint. 

# read_write_test.py
from locust import HttpUser, task, between
# ... imports ...

class ReadHeavyUser(HttpUser):
    weight = 10
    @task(9)
    def read_data(self):
        self.client.get("/api/doctors", name="Read: Get Doctors")
        
    @task(1)
    def write_data(self):
        # Payload aleatorio
        self.client.post("/api/doctors", json={...}, name="Write: Create Doctor")

class WriteHeavyUser(HttpUser):
    weight = 10
    @task(2)
    def read_data(self):
        self.client.get("/api/patients", name="Read: Get Patients")
        
    @task(8)
    def write_data(self):
        self.client.post("/api/patients", json={...}, name="Write: Create Patient")

6.3 Análisis Detallado y Comparativa

Hallazgo Principal: El sistema es 3.4 veces más rápido leyendo que escribiendo.
  • Degradación del Throughput: Pasamos de ~145 RPS en Read-Heavy a ~42 RPS en Write-Heavy. Esto es normal, ya que una inserción en BD implica: validación de constraints, escritura en disco (WAL), actualización de índices y commit de transacción. La lectura, en cambio, suele ser directa o cacheada.
  • Latencia (p95): El tiempo de respuesta subió de 28ms a 185ms. Esto indica que, bajo concurrencia, los usuarios experimentarán una espera perceptible al guardar datos, aunque sigue estando por debajo de 1 segundo (aceptable).
  • Integridad de Datos: En el escenario Write-Heavy aparecieron errores 409 (Conflict). Esto es positivo: significa que el sistema evitó exitosamente la creación de registros duplicados cuando múltiples usuarios intentaron crear el mismo recurso simultáneamente.

7. Conclusiones

Diagnóstico del Sistema

El sistema PredictHealth está optimizado para cargas de lectura, lo cual es adecuado para su propósito (consulta de expedientes). Sin embargo, el módulo de escritura presenta una latencia mayor que podría requerir atención si se espera un volumen masivo de registros simultáneos.

Recomendaciones

  • Optimización de Escritura: Revisar los índices en la base de datos. Demasiados índices pueden estar ralentizando los INSERTs.
  • Escalabilidad Asíncrona: Para cargas Write-Heavy futuras, considerar usar una cola de mensajes (RabbitMQ/Kafka) para procesar las creaciones en segundo plano y no bloquear la respuesta HTTP al usuario.
