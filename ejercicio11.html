Ejercicio Guiado 11: Pruebas Spike en Locust

1. Introducción

En este reporte documentamos la ejecución de una Prueba Spike. A diferencia de las pruebas de carga convencionales o de Ramp-up gradual, una prueba Spike somete al sistema a un incremento de tráfico extremo y casi instantáneo, seguido de una bajada igual de drástica.

El objetivo es simular escenarios de "avalancha", para evaluar si la arquitectura de PredictHealth colapsa o sobrevive a la presión repentina.

2. Objetivos de la Prueba

  • Medir la respuesta del sistema (latencia y errores) ante un pico abrupto de 200 a 1000 usuarios en 10 segundos.
  • Verificar si el sistema "degrada con gracia" (sin caídas totales) y si la latencia p95 se recupera tras el pico.
  • Observar los efectos de posibles mecanismos de protección (ej. errores 429 Too Many Requests, 503 Service Unavailable, o timeouts).

3. Metodología

Arquitectura del Entorno de Prueba

Las pruebas se ejecutaron desde una máquina local que actuaba como nodo maestro de Locust, generando tráfico HTTP hacia los servicios desplegados. Los componentes del sistema (CMS y microservicios) estaban corriendo localmente a través de Docker Compose.

4. Descripción de los Escenarios de Carga

Utilizamos un patrón de carga personalizado llamado "DoubleWaveShape". Este escenario no es lineal; está diseñado para golpear al sistema con dos oleadas consecutivas de alta intensidad.

Perfil del Spike (La Doble Ola)

  1. Valle (Baseline): Tráfico bajo y constante de 20 usuarios.
  2. Spike 1: Subida repentina a 200 usuarios concurrentes.
  3. Recuperación 1: Caída inmediata de vuelta a 20 usuarios.
  4. Spike 2: Segunda subida repentina a 200 usuarios (para probar la fatiga del sistema).
  5. Recuperación Final: Retorno al estado de reposo.

Interpretación Técnica

Hallazgo Principal: El sistema sobrevivió, pero el servicio de autenticación es el cuello de botella.
  • Resiliencia de Lectura: Los microservicios de negocio (Doctores, Pacientes) soportaron el pico de 200 usuarios sin generar un solo error (0% Failures). Esto confirma que la estrategia de usar Redis y contenedores ligeros funciona bien para servir contenido.
  • Colapso Parcial en Auth: El endpoint /auth/login falló el 31% de las veces durante el pico. Esto se debe a un fenómeno conocido como "Thundering Herd" (Estampida). Cuando 200 usuarios intentan hashear contraseñas y firmar tokens JWT en el mismo segundo, la CPU del contenedor de Auth se satura, provocando Timeouts (latencias > 1900ms).
  • Recuperación Exitosa: Lo más positivo de la prueba es la capacidad de recuperación. En los "valles" (cuando la carga bajó a 20 usuarios), la tasa de error volvió a 0% y la latencia se estabilizó instantáneamente. El sistema no quedó en un estado "zombie" ni requirió reinicio manual.

7. Conclusiones

Diagnóstico del Sistema

La arquitectura es elástica y robusta para usuarios ya autenticados. Sin embargo, el proceso de entrada (Login) es frágil ante picos repentinos. Si 200 personas intentan entrar al mismo tiempo, 60 de ellas recibirán un error.

Recomendaciones

  • Escalar Servicio de Auth: Aumentar el número de réplicas del contenedor auth-service (mínimo 3 réplicas) para distribuir la carga de CPU del hashing de contraseñas.
  • Queue de Login: Implementar un mecanismo de espera o "Rate Limiting" en el API Gateway para suavizar el pico de peticiones de login, evitando que lleguen todas juntas al microservicio.
