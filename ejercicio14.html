Ejercicio Guiado 14: Pruebas CSV Feeder en Locust

1. Introducción

En este reporte analizamos la prueba de CSV Feeder (Alimentador de Datos). A diferencia de las pruebas de carga anteriores que se enfocaban en el estrés del servidor, esta prueba se centra en la validación de la integridad de los datos de prueba. Utilizamos usuarios reales simulados para verificar que las credenciales almacenadas en nuestro archivo de control (CSV) coincidan perfectamente con los registros poblados en la base de datos, un paso crítico para garantizar la validez de cualquier prueba de rendimiento subsecuente.

2. Objetivos de la Prueba

  • Validar la capacidad del servicio de autenticación (/auth/login) para manejar logins concurrentes con credenciales únicas.
  • Medir la tasa de error de sincronización entre los datos de prueba (users.csv) y la base de datos poblada (populate.sql).
  • Registrar la latencia y tasa de peticiones de los logins exitosos.

3. Metodología

Arquitectura del Entorno

La prueba utiliza el entorno estándar dockerizado, pero se enfoca en el flujo de inicialización de sesión.

[Locust (CSV Reader)] -> [API Gateway] -> [Auth Service] -> [PostgreSQL Users DB]

Herramientas Utilizadas

  • Locust: Versión 2.41.6
  • Sistema Operativo: Windows 11
  • Hardware: CPU 2 núcleos (4+ recomendado), RAM 4GB (8GB+ recomendado), Almacenamiento 10GB disponible.
  • Infraestructura:
    • Docker (v20.10+) y Docker Compose (v2.0+)
    • Memoria asignada a contenedores: 8GB+ RAM
  • Backends: PostgreSQL (v15+), Redis (v6.0+) con soporte para 20+ conexiones simultáneas.
  • Lenguaje: Python 3.11+

4. Descripción de los Escenarios de Carga

Esta prueba es un proceso de dos pasos diseñado para cumplir con los requisitos de integridad de datos del proyecto:

Paso 1: Poblar la Base de Datos

Antes de la ejecución, se utilizó un script auxiliar (populate.sql) para registrar masivamente más de 300 usuarios en la base de datos de PostgreSQL. Este script inserta los datos del usuario y una contraseña ya hasheada (ej. con bcrypt) para simular un entorno de producción real.

Paso 2: Simular Logins

Durante la ejecución de las pruebas (analizado aquí usando los datos de la Prueba Soak), Locust utiliza el archivo users.csv que contiene las contraseñas en texto plano. Cada usuario virtual de Locust lee un par de (email, contraseña) del CSV e intenta autenticarse contra el endpoint /auth/login.

El objetivo es medir la fricción entre estos dos pasos: ¿coinciden los datos del CSV con los datos de la base de datos?

6. Resultados e Interpretación

Métricas de Autenticación (Extraídas de la Prueba Soak)

Los siguientes datos se extrajeron de la Prueba Soak (30 minutos, 90 usuarios), ya que proporciona la muestra estadística más grande de intentos de login. Para esta prueba, la métrica principal es el rendimiento del endpoint de autenticación.

Estadísticas del Endpoint de Autenticación

Endpoint Peticiones Errores Tasa de Error (%) RPS p50 (ms) p95 (ms)
/auth/login 824 61 7.40% 0.46 614.96 868.52

Interpretación de los Resultados

Hallazgo Crítico: Discrepancia de Datos Detectada.

Esta "prueba" fue la más crítica de todo el reporte, ya que identificó exitosamente la causa raíz de la mayoría de los errores vistos en las otras pruebas.

  • Objetivo 1 (Logins Concurrentes): El sistema procesó 824 inicios de sesión únicos de forma concurrente. La latencia de los logins exitosos es aceptable con un p95 de 868.52 ms. El login es una operación lenta por diseño (debido al hash de la contraseña), por lo que un valor por debajo de 1 segundo es un buen resultado funcional.
  • Objetivo 2 (Sincronización de Datos): El hallazgo clave es la tasa de error del 7.40% en /auth/login. Esto significa que 61 de los 824 intentos de login fallaron.
    Diagnóstico: Los archivos populate.sql (que pobla la BD) y users.csv (que usa Locust) no están perfectamente sincronizados. Existe un 7.40% de usuarios en el CSV que no existen en la base de datos o cuyas contraseñas no coinciden.
  • Objetivo 3 (Tasas de Login): Se registró una tasa de login sostenida de 0.46 RPS (o aprox. 27 logins por minuto) durante la prueba Soak. La lógica on_start (implementada en common/users.py) garantiza que cada usuario obtenga su propio token, cumpliendo el objetivo de no reutilizar tokens.

7. Conclusiones y Recomendaciones

Diagnóstico de Datos

La prueba ha sido exitosa en su propósito de validación: ha revelado que nuestros datos de prueba tienen un 92.6% de integridad, pero ese 7.4% de error es suficiente para generar ruido en las pruebas de carga.

Acciones Recomendadas

  • Sincronización Inmediata: Regenerar el archivo users.csv extrayendo los datos directamente de la base de datos de prueba después de ejecutar el script populate.sql, para asegurar una coincidencia del 100%.
  • Limpieza de Pruebas: Antes de la certificación final, se debe asegurar que la tasa de error en Login sea 0% para no enmascarar problemas reales de rendimiento.
