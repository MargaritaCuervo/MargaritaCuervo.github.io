Ejercicio Guiado 7: Pruebas Baseline de Arquitectura Completa

Introducción

En este ejercicio, me enfoqué en realizar la prueba "Baseline" (Línea Base) de todo el ecosistema PredictHealth. A diferencia de las pruebas unitarias o de microservicios aislados, aquí mi objetivo fue someter a carga la arquitectura completa, incluyendo el CMS (Frontend) y los 4 microservicios principales (Gateway, Autenticación, Médicos y Pacientes) funcionando en conjunto.

Esta prueba es fundamental porque me permite conocer el estado "normal" del sistema bajo una carga controlada, estableciendo métricas de referencia (tiempos de respuesta y tasas de error) que me servirán para comparar futuras optimizaciones o detecciones de regresión.

Objetivos Personales

  • Simulación Realista: Configurar un escenario en Locust que imite el comportamiento de usuarios reales navegando por el CMS e interactuando con múltiples microservicios simultáneamente.
  • Prueba de Integración bajo Carga: Verificar que la comunicación entre el API Gateway y los servicios internos (Auth, Doctors, Patients) no se degrade al aumentar la concurrencia.
  • Análisis de Cuellos de Botella: Identificar qué microservicio específico presenta mayor latencia o tasa de fallos (4xx/5xx) durante la ejecución.

Desarrollo de la Prueba

Para llevar a cabo esta prueba, desarrollé el script baseline_test.py. Diseñé este script para que no solo golpeara un endpoint, sino que realizara un flujo completo de negocio: autenticación de usuario, obtención de tokens y consultas posteriores a la base de datos de médicos y pacientes.

1. Configuración del Entorno y Datos

Utilicé un archivo de datos masivos llamado users.csv para parametrizar las pruebas. Esto fue esencial para evitar que el sistema bloqueara las peticiones por usar siempre el mismo usuario y para simular una concurrencia real de sesiones distintas.

Nota: El archivo users.csv se encuentra incluido en el ZIP de descarga al final de este reporte. Debido a su gran tamaño y peso, no se visualiza directamente en este documento HTML, pero es parte integral de la ejecución del script.

2. Código Implementado (baseline_test.py)

A continuación, presento el código que utilicé. En la clase PredictHealthUser definí las tareas con pesos específicos (`@task`) para dar más relevancia a las consultas de lectura (GET) que son más frecuentes en el CMS, frente a las escrituras (POST). 


from locust import HttpUser, task, between
import pandas as pd
import random

# Carga de datos del CSV (users.csv incluido en el ZIP)
# Utilicé pandas para una lectura eficiente de los credenciales
csv_file_path = "users.csv"
data = pd.read_csv(csv_file_path)

class PredictHealthUser(HttpUser):
    wait_time = between(1, 5)  # Simula tiempo de lectura/pensamiento del usuario

    def on_start(self):
        """
        Al iniciar cada usuario virtual, selecciono credenciales aleatorias
        del CSV y realizo el login contra el microservicio de Auth.
        """
        user_row = data.sample(n=1).iloc[0]
        self.email = user_row['email']
        self.password = user_row['password']
        
        response = self.client.post("/auth/login", json={
            "email": self.email,
            "password": self.password
        })
        
        if response.status_code == 200:
            self.token = response.json().get("access_token")
        else:
            self.token = None

    @task(4)
    def get_doctors(self):
        """Consulta al microservicio de Doctores (Alta frecuencia)"""
        if self.token:
            headers = {"Authorization": f"Bearer {self.token}"}
            self.client.get("/api/doctors", headers=headers, name="CMS: List Doctors")

    @task(4)
    def get_patients(self):
        """Consulta al microservicio de Pacientes (Alta frecuencia)"""
        if self.token:
            headers = {"Authorization": f"Bearer {self.token}"}
            self.client.get("/api/patients", headers=headers, name="CMS: List Patients")

Interpretación de mis Hallazgos:

Al analizar la tabla de resultados (Fig 1), observé los siguientes puntos críticos sobre el comportamiento de los 4 microservicios integrados:

  • Estabilidad del CMS y Gateway: El sistema logró procesar un alto volumen de peticiones (RPS) manteniendo tiempos de respuesta aceptables en la mayoría de los endpoints de lectura (GET).
  • Errores de Autenticación (401): Noté una cantidad considerable de respuestas 401 en el endpoint /login. Al revisar los logs, determiné que esto se debió a inconsistencias en algunos registros del archivo users.csv (usuarios que no existían en la BD del entorno de pruebas), lo cual es un hallazgo válido sobre la calidad de los datos de prueba.
  • Errores de Procesamiento (422): Identifiqué fallos 422 (Unprocessable Entity) en los endpoints de creación. Esto indica que las validaciones de negocio en los microservicios están funcionando correctamente al rechazar datos duplicados o formatos inválidos enviados por el script bajo estrés.
