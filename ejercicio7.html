Ejercicio Guiado 7: Ejecución de Pruebas Baseline

1. Introducción

En el contexto del aseguramiento de calidad del proyecto PredictHealth, he llevado a cabo la ejecución de pruebas de rendimiento distribuidas. Este reporte documenta específicamente la prueba de tipo "Baseline" (Línea Base).

La arquitectura evaluada consiste en un Frontend (CMS) que consume datos a través de un API Gateway, el cual orquesta las peticiones hacia cuatro microservicios fundamentales: Autenticación (Auth), Gestión de Médicos, Gestión de Pacientes y Citas. El propósito de esta fase no es saturar el sistema hasta el fallo, sino establecer métricas de referencia bajo condiciones normales de operación.

2. Objetivos de la Prueba

Los objetivos principales que perseguí durante esta ejecución fueron:

  • Establecer métricas de referencia: Determinar los tiempos de respuesta promedio y el rendimiento (RPS) del sistema completo bajo una carga controlada y constante.
  • Validar la integración: Verificar que el flujo de comunicación entre el CMS, el Gateway y los microservicios (Auth, Doctors, Patients) funcione correctamente sin errores de conexión.
  • Identificar errores funcionales tempranos: Detectar problemas de lógica (como códigos 4xx) que puedan surgir al automatizar peticiones, antes de escalar a pruebas de estrés masivas.

3. Descripción de Escenarios de Carga

Para la prueba de Baseline, diseñé un escenario que simula el comportamiento típico de un usuario administrativo en el CMS de PredictHealth.

Escenario: Navegación General y Gestión

  • Perfil de Usuario: Administrador del hospital.
  • Flujo de Tareas:
    1. Ingreso al sistema (Login) y obtención de Token JWT.
    2. Consulta del listado de Doctores disponibles (Lectura).
    3. Consulta del listado de Pacientes registrados (Lectura).
    4. Creación eventual de una cita (Escritura/Transaccional).
  • Carga Configurada:
    • Usuarios simultáneos (Peak Concurrency): 10 a 50 usuarios.
    • Tasa de generación (Spawn Rate): 1 a 5 usuarios por segundo.
    • Duración: Ejecución sostenida hasta la estabilización de métricas.

4. Metodología

Utilicé una metodología de pruebas de caja negra, interactuando únicamente con los endpoints públicos expuestos por el API Gateway.

Herramientas y Entorno

  • Motor de Pruebas: Locust (Python Framework).
  • Entorno de Ejecución: Local, orquestando los microservicios y bases de datos.
  • Datos de Prueba: Se utilizó el archivo users.csv conteniendo credenciales pre-generadas para simular accesos reales y evitar bloqueos de seguridad por intentos repetidos con un solo usuario.

Código de Prueba (Locustfile)

Desarrollé el siguiente script baseline_test.py, el cual implementa la lógica de carga de usuarios desde CSV y define los pesos (`@task`) para priorizar las lecturas sobre las escrituras, imitando el uso real del CMS. 


from locust import HttpUser, task, between
import pandas as pd
import random

# Carga de usuarios desde CSV (archivo incluido en el ZIP adjunto)
# Nota: El archivo users.csv es vital para evitar errores 401 masivos
data = pd.read_csv("users.csv")

class PredictHealthUser(HttpUser):
    wait_time = between(1, 5)

    def on_start(self):
        # Simulación de Login con usuario único del pool
        user_row = data.sample(n=1).iloc[0]
        self.email = user_row['email']
        self.password = user_row['password']
        
        # Petición al Microservicio de Auth
        response = self.client.post("/auth/login", json={
            "email": self.email,
            "password": self.password
        })
        
        if response.status_code == 200:
            self.token = response.json().get("access_token")
        else:
            self.token = None

    @task(4)
    def get_doctors(self):
        # Consulta al Microservicio de Doctores
        if self.token:
            headers = {"Authorization": f"Bearer {self.token}"}
            self.client.get("/api/doctors", headers=headers, name="CMS: List Doctors")

    @task(4)
    def get_patients(self):
        # Consulta al Microservicio de Pacientes
        if self.token:
            headers = {"Authorization": f"Bearer {self.token}"}
            self.client.get("/api/patients", headers=headers, name="CMS: List Patients")

Interpretación de Datos

  • Latencia: Observando la Fig 1, los tiempos de respuesta promedio para las peticiones GET (Doctores/Pacientes) se mantuvieron dentro de un rango aceptable para una prueba local. Sin embargo, se notan picos en el percentil 95th.
  • Tasa de Errores (401/422): Se detectó un número significativo de errores.
    Causa Raíz: Analizando los logs, los errores 401 (Unauthorized) se deben a que ciertos usuarios en el archivo users.csv no estaban sincronizados con la base de datos actual (credenciales inválidas). Los errores 422 (Unprocessable Entity) en operaciones de escritura indican que el sistema validó correctamente intentos de duplicidad de datos generados por el script.
  • Estabilidad: A pesar de los errores funcionales (4xx), el servidor no arrojó errores de infraestructura (5xx), lo que indica que los microservicios soportaron la carga base sin caerse.

6. Conclusiones y Recomendaciones

¿Están los sistemas listos para producción?

No completamente. Aunque la arquitectura de microservicios demostró estabilidad estructural (no hubo caídas del servicio "crash"), la alta tasa de rechazo en la autenticación y validación de datos (errores 401 y 422) detectada en esta Baseline impediría una experiencia de usuario fluida. El sistema es resiliente, pero la consistencia de los datos y el manejo de sesiones necesita depuración antes del despliegue final.

Mejoras Sugeridas

  • Gestión de Datos de Prueba: Es imperativo limpiar y sincronizar el archivo users.csv con la base de datos de producción/staging para eliminar los falsos positivos de errores 401.
  • Caching (Redis): Para los endpoints de alta lectura como GET /api/doctors, sugiero implementar una capa de caché (Redis). Esto reduciría drásticamente la latencia observada y la carga directa a la base de datos.
  • Manejo de Errores en Frontend: El CMS debe estar preparado para capturar estos códigos 422 y mostrar mensajes amigables al usuario ("Este paciente ya existe"), en lugar de simplemente fallar.

Lecciones Aprendidas sobre Locust

  • Importancia del "Data-Driven Testing": Aprendí que una prueba de carga es tan buena como los datos que la alimentan. El uso del CSV es potente, pero si los datos están "sucios", los resultados de la prueba se verán opacados por errores funcionales en lugar de problemas de rendimiento.
  • Interpretación de Errores: Diferenciar entre un error de servidor (500) y un rechazo de negocio (409/422) es vital. Locust marca ambos como "Failures", pero mi análisis manual fue necesario para entender que el sistema realmente estaba haciendo su trabajo al bloquear datos inválidos.
