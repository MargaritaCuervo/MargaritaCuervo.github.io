Ejercicio Guiado 7: Pruebas Baseline en Locust

1. Introducción

En este reporte presentamos los resultados de la ejecución de la prueba de carga tipo "Baseline" para el sistema PredictHealth. El propósito fundamental de este ejercicio fue establecer una línea base de rendimiento del sistema completo, incluyendo el CMS y los cuatro microservicios core, operando bajo condiciones controladas. Esta fase es crítica para identificar el comportamiento estándar de la arquitectura antes de someterla a escenarios de estrés máximo.

2. Objetivos de la Prueba

Como equipo, definimos los siguientes objetivos para esta sesión:

  • Validar la robustez del flujo de autenticación (login) bajo carga concurrente, midiendo la tasa de éxito utilizando credenciales parametrizadas.
  • Establecer la línea base de latencia (percentiles 50 y 95) y throughput (Peticiones por Segundo - RPS) para las operaciones CRUD autenticadas.
  • Identificar proactivamente fallos de autorización (Errores 401) y validación de negocio (Errores 422), diferenciándolos de fallos de infraestructura (Errores 500).

3. Metodología

Arquitectura del Entorno de Prueba

Las pruebas se ejecutaron desde una máquina local que actuaba como nodo maestro de Locust, generando tráfico HTTP hacia los servicios desplegados. Los componentes del sistema (CMS y microservicios) estaban corriendo localmente a través de Docker Compose, lo que asegura un entorno aislado y consistente para la evaluación.

La arquitectura general de la prueba sigue el siguiente flujo:

[Máquina Local (Locust Master)] -> [Red Local (Docker Network)] -> [Contenedores de CMS y Microservicios] -> [Contenedores de PostgreSQL y Redis]

Las URLs base configuradas para cada servicio bajo prueba fueron las siguientes:

  • CMS: http://localhost:80
  • Servicio Auth-JWT: http://localhost:5000
  • Servicio de Instituciones: http://localhost:5001
  • Servicio de Doctores: http://localhost:5002
  • Servicio de Pacientes: http://localhost:5003

Herramientas Utilizadas

  • Locust: Versión 2.41.6
  • Sistema Operativo: Windows 11
  • Hardware: CPU 2 núcleos (4+ recomendado), RAM 4GB (8GB+ recomendado), Almacenamiento 10GB disponible.
  • Infraestructura:
    • Docker (v20.10+) y Docker Compose (v2.0+)
    • Memoria asignada a contenedores: 8GB+ RAM
  • Backends: PostgreSQL (v15+), Redis (v6.0+) con soporte para 20+ conexiones simultáneas.
  • Lenguaje: Python 3.11+

4. Descripción de los Escenarios de Carga

A continuación, detallamos la configuración específica utilizada para la prueba Baseline.

  • Archivo: baseline_test.py
  • Comportamiento General: La prueba se configuró para simular 150 usuarios concurrentes en total, divididos equitativamente según las variables de entorno:
    • 50 DoctorUser
    • 50 PatientUser
    • 50 InstitutionUser

Detalle de Tareas por Rol:

  • Tareas (DoctorUser): Ejecuta un flujo de tareas de lectura (get_all_doctors, get_doctor_details) y escritura (create_doctor), excluyendo las tareas marcadas como "smoke".
  • Tareas (PatientUser): Ejecuta tareas de lectura (get_all_patients, get_patient_details) y escritura (create_patient).
  • Tareas (InstitutionUser): Ejecuta tareas de lectura (get_all_institutions, search_institution) y escritura (create_institution).

Alimentación de Datos (CSV Feeder):

Todos los usuarios realizan una operación de login al inicio (on_start) utilizando credenciales únicas extraídas del archivo users.csv para obtener un token JWT válido antes de iniciar sus tareas.

Interpretación de la Prueba Baseline

El Problema No es el Rendimiento, es la Autorización

Los resultados de la prueba baseline revelaron un hallazgo crítico que no está relacionado con el rendimiento del servidor, sino con la lógica de autenticación y los datos de prueba. La métrica más importante de esta prueba es la tasa de error del 5.99%. Como se evidencia en la tabla de fallos extraída del reporte de Locust, todos los errores fueron de tipo 401 UNAUTHORIZED. Esto significa que el servidor no se cayó ni se puso lento; al contrario, funcionó correctamente al rechazar peticiones no autorizadas.

Desglose y Análisis de los Fallos

  • Fallos en POST /auth/login: Este es el origen del problema. Una parte de los usuarios simulados intentó iniciar sesión con credenciales inválidas. Esto indica una inconsistencia entre el archivo users.csv y la base de datos de usuarios registrados. Es probable que esos usuarios no existieran o tuvieran contraseñas incorrectas.
  • Fallos en POST /api/v1/doctors y POST /api/v1/patients: Este es un efecto secundario directo del fallo anterior. Cuando un usuario no puede iniciar sesión, su token JWT no es generado. Por lo tanto, cualquier intento posterior de realizar una acción protegida (como crear un doctor o paciente) resulta en un error 401 UNAUTHORIZED.

Rendimiento de las Peticiones Exitosas

A pesar de los fallos de autenticación, el 94% de las peticiones fueron exitosas y mostraron un rendimiento excelente. Con un tiempo de respuesta p95 de 48.34 ms, queda demostrado que la infraestructura (servicios, base de datos y caché) es muy rápida y capaz de manejar la carga sin degradación de la latencia.

6. Conclusiones y Recomendaciones

¿Son los sistemas listos para producción?

Sí, en términos de rendimiento. La infraestructura demostró tiempos de respuesta excepcionales (< 50ms) bajo carga. Sin embargo, la integridad de los datos de prueba debe ser corregida antes de la siguiente fase para evitar el ruido generado por los errores de autenticación.

Mejoras Sugeridas

  • Sincronización de Datos: Regenerar el archivo users.csv asegurando que todos los usuarios listados existan realmente en la base de datos de prueba.
  • Manejo de Tokens: Revisar el script de Locust para asegurar que, si el login falla, el usuario no intente ejecutar tareas posteriores que requieran token, evitando así la cascada de errores 401.
