Ejercicio Guiado 6: Pruebas locales con Locust

Introducción

En el desarrollo de microservicios, asegurar que la aplicación pueda soportar múltiples peticiones simultáneas es crucial. Para este ejercicio, utilizamos Locust, una herramienta de pruebas de carga de código abierto escrita en Python. El propósito es simular el comportamiento de usuarios reales interactuando con el microservicio de "Books", permitiéndonos medir tiempos de respuesta y detectar errores de concurrencia antes de un despliegue en producción.

Objetivos

  • Configurar el entorno de pruebas: Implementar el script locustfile.py definiendo el comportamiento de un usuario estándar (registro, login, consultas y creación de libros).
  • Ejecutar simulación de carga: Realizar pruebas locales simulando 10 usuarios concurrentes para estresar los endpoints de la API.
  • Analizar métricas de rendimiento: Interpretar los resultados obtenidos en la interfaz web de Locust, identificando latencias promedio y validando el manejo de errores (códigos 409 y 200).

Desarrollo

La práctica consistió en la creación de un script en Python que define un HttpUser. Este usuario virtual ejecuta tareas secuenciales que cubren el flujo completo de la aplicación, desde la autenticación hasta la gestión del inventario de libros.

2. Script de Prueba (locustfile.py)

El código implementado define una clase BookstoreUser. Se establecieron pesos (tasks weights) para dar más prioridad a tareas de lectura (como get_all_books) sobre las de escritura, simulando un tráfico realista. 


from locust import HttpUser, task, between, SequentialTaskSet
import json
import random

class BookstoreTaskSet(SequentialTaskSet):
    """
    Conjunto de tareas secuenciales que simulan el flujo de un usuario real
    """
    
    def on_start(self):
        """Se ejecuta cuando un usuario virtual inicia"""
        self.username = f"user_{random.randint(1000, 999999)}"
        self.password = "testpass123"
        self.access_token = None
        self.register_user()
        self.login_user()
    
    def register_user(self):
        self.client.post(
            "/auth/register",
            json={"username": self.username, "password": self.password},
            name="AUTH: Register"
        )
    
    def login_user(self):
        response = self.client.post(
            "/auth/login",
            json={"username": self.username, "password": self.password},
            name="AUTH: Login"
        )
        if response.status_code == 200:
            self.access_token = response.json().get("access_token")

    def get_headers(self):
        if self.access_token:
            return {"Authorization": f"Bearer {self.access_token}"}
        return {}
    
    @task(5)
    def get_all_books(self):
        self.client.get("/api/books", headers=self.get_headers(), name="BOOKS: Get All")
    
    @task(1)
    def create_book(self):
        # Datos aleatorios para simular creación
        book_data = {
            "isbn": f"978-{random.randint(10000,99999)}",
            "titulo": f"Libro Prueba {random.randint(1, 9999)}",
            "id_autor": random.randint(1, 10),
            "price": round(random.uniform(10.0, 100.0), 2),
            "formato": "Digital"
        }
        self.client.post("/api/books/create", json=book_data, headers=self.get_headers(), name="BOOKS: Create")

class BookstoreUser(HttpUser):
    tasks = [BookstoreTaskSet]
    wait_time = between(1, 3)
    host = "http://127.0.0.1:5000"

3. Análisis de Resultados y Métricas

Tabla de Estadísticas (Statistics):
La tabla resume el comportamiento de cada endpoint. El endpoint más estresado fue GET /api/books (obtener lista de libros) con 320 peticiones.

  • Latencia: El tiempo de respuesta promedio (Average) se mantuvo en 216ms, lo cual es un tiempo aceptable para una respuesta local.
  • Concurrencia: Se logró mantener una tasa de 12.2 RPS (Peticiones por Segundo) constantes sin caídas del servidor.
  • Errores: Los fallos en /auth/register no son errores del servidor, sino respuestas HTTP 409 esperadas al intentar registrar usuarios ya existentes.
Fig 2. La tabla muestra una latencia media estable (~200ms) y una distribución de carga correcta entre lectura y escritura.

Interpretación de Gráficos (Charts):
El análisis visual nos permite correlacionar la carga de usuarios con el rendimiento del servidor.

1. Rendimiento y Estabilidad (RPS vs Latencia):
En la siguiente gráfica observamos dos métricas clave:

  • Línea Verde (Total Requests per Second): Muestra el caudal de peticiones. Se estabilizó rápidamente en unas 12-13 peticiones/segundo y se mantuvo constante (línea plana), lo que indica que el servidor no se saturó y pudo atender la demanda continua.
  • Línea Morada (95th Percentile Response Time): Muestra el tiempo de respuesta. Se observa un pico inicial de casi 700ms. Este comportamiento es normal durante la fase de "calentamiento" (Ramp-up), donde el sistema está procesando los registros y logins simultáneos. Una vez que los usuarios se estabilizaron, la latencia cayó y se mantuvo estable cerca de los 200ms.
Fig 3. La línea verde (RPS) muestra estabilidad en el procesamiento. La línea morada muestra cómo el tiempo de respuesta se estabiliza tras el pico inicial.

2. Correlación con el Número de Usuarios:
Esta gráfica confirma la causa del pico de latencia mencionado arriba.

  • Línea Azul (Number of Users): Muestra la rampa de subida (Ramp-up) de 0 a 10 usuarios.
  • Podemos ver claramente que el pico de latencia (línea morada) coincide exactamente con la subida de la línea azul. Esto nos dice que el sistema sufre un poco más de estrés al crear las sesiones (Login/Register), pero una vez que los 10 usuarios están activos (la línea azul se aplana), el sistema entra en un estado estable y rápido.
Fig 4. Comparativa: A medida que los usuarios (azul) llegan al máximo, el tiempo de respuesta (morada) se estabiliza.

Análisis de Errores:
Se registraron fallos específicos en el endpoint /auth/register. Al revisar la pestaña de "Failures", confirmamos que se trata de errores 409 Conflict. Esto es un comportamiento esperado y correcto del microservicio, ya que indica que Locust intentó registrar un nombre de usuario que ya existía en la base de datos debido a la aleatoriedad del script.

Conclusión

La implementación de pruebas de carga con Locust permitió validar satisfactoriamente el rendimiento del microservicio de Libros. Se logró simular un escenario de tráfico moderado donde el sistema respondió con latencias aceptables (promedio ~200ms). Además, la detección de errores 409 confirmó que las validaciones de lógica de negocio (evitar usuarios duplicados) están funcionando correctamente bajo estrés. Esta práctica demuestra la importancia de automatizar pruebas de rendimiento para asegurar la estabilidad de las APIs antes de su integración final.
